# Content Duplication Audit

Audit date: 2026-06-11

## Scope

This audit covers the current public, booking, and admin implementation surfaces
for duplicated or hardcoded content that should eventually move into shared
CMS-ready local structures.

The repository is still at a scaffold stage. No route content was rewritten in
this step.

## Local Guidance Reviewed

- `AGENTS.md`
- `skills/data-and-cms.md`

External project references were inspected for audit and CMS ownership document
shape only. No client-specific content, code, assets, or data was copied.

## Findings

### F1: No Shared Content Source Exists Yet

`app/(pages)/(home)/content.js` is empty, so there is currently no shared local
source for page copy, service data, booking labels, site settings, or admin copy.

Impact:

- Future public, booking, and admin work will likely introduce duplicate literals
  unless a shared content boundary is established first.
- The existing route structure already suggests a local content-file pattern, but
  it is not populated.

Recommended owner for next steps:

- Create a CMS-ready local content module for shared site settings, public page
  sections, service records, booking inquiry options, and admin display copy.

### F2: Placeholder Brand And Metadata Are Hardcoded

The only visible public copy is `Virtue Generated` in
`app/(pages)/(home)/page.jsx`. The global metadata in `app/layout.jsx` still uses
`Create Next App` and `Generated by create next app`.

Impact:

- Public page title, metadata, and visible copy are inconsistent with the
  atelier bookings product goal.
- Metadata will become duplicated if each future route defines its own business
  name, description, and CTA language independently.

Recommended owner for next steps:

- Put business identity, default SEO title, default description, contact labels,
  and primary CTA labels in a shared local `site` or `settings` object before
  expanding route copy.

### F3: Public, Booking, And Admin Data Shapes Are Not Defined

No booking or admin records were found. There are also no service records,
package records, inquiry option arrays, status labels, or dashboard summaries.

Impact:

- There are no conflicting structures yet, but there is also no contract for the
  future CMS migration.
- Booking forms and admin tables could drift if they each define service names,
  statuses, intake fields, or client labels locally.

Recommended owner for next steps:

- Define repeatable local records with stable IDs and explicit status fields
  before rendering them in public, booking, or admin screens.
- Keep provider-specific database IDs out of these local mock structures.

### F4: README Still References Default Scaffold Paths

`README.md` says to edit `app/page.js`, but the current public page is under
`app/(pages)/(home)/page.jsx`.

Impact:

- Handoff documentation currently conflicts with the actual route layout.
- This is not runtime content duplication, but it is stale product documentation
  that can mislead later implementation work.

Recommended owner for next steps:

- Update README or add handoff documentation after the CMS-ready local content
  structure exists.

## CMS-Ready Content Candidates

The next implementation step should avoid scattering these across components:

- `siteSettings`: business name, short description, default metadata, contact
  labels, social links, navigation labels, CTA labels.
- `pages.home`: hero copy, service discovery section copy, trust/proof copy,
  booking CTA copy.
- `services`: repeatable service records with `id`, `slug`, `title`,
  `summary`, `duration`, `startingPrice`, `status`, and `sortOrder`.
- `bookingInquiry`: form intro copy, field labels, selectable service IDs,
  timeline options, budget options, preferred contact methods, success/error
  messages.
- `adminDashboard`: dashboard labels, booking status labels, empty states, table
  column labels, quick filters.
- `mockBookings`: local admin records for future dashboard rendering with
  serialized dates and stable local IDs.

## Suggested Ownership Boundary

Use three layers while the project is local-content backed:

1. Shared CMS-ready local structures own repeatable records, business identity,
   form options, status labels, and reusable CTA copy.
2. Route content files own page-specific section framing when it is not reused
   elsewhere.
3. Components own rendering behavior, layout, validation display, and
   interaction state only.

## Not Changed In This Step

- No public page copy was replaced.
- No booking routes or admin screens were created.
- No database, auth, payment, environment, cron, or deployment behavior was
  changed.
- No dependencies were added.
